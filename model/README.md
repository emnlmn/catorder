# CatOrder next-order model (catorder-nbr-v1)

A small PyTorch model (122k parameters, 0.5 MB) that reads a customer's order history and predicts when they will order next, how likely they are to stop ordering, and what the next basket will hold (products and quantities). It is not an LLM and has no hand-written rules. The weights in `weights/` were trained on an **AMD Radeon Pro W7900D with ROCm** (PyTorch 2.13.0+rocm10.0.0) in 169 s; the log is `logs/train_amd.log`.

CatOrder uses it in three places: the Forecast page (who is late, who is coming up, next week's demand per product), the "Usually also takes" suggestions in a draft order, and the feedback the seller gives on those suggestions, which is stored for the next training run.

All training and test data is synthetic. The numbers below show what the model learns from patterns we wrote; they are not results on a real distributor.

## How it works

- **Input:** the customer's last 16 orders, each as per-product log quantity, the gap since the previous order, day of year and weekday (sin/cos), plus the customer kind.
- **Network:** a GRU over the orders, a kind embedding and cadence context feed a shared trunk with four heads:
  - next gap in days (Laplace, median), trained as of the day of the last order;
  - churn: no order within 60 days, trained at several offsets after the last order so it learns "overdue";
  - per product: chance it is in the next order (BCE) and its quantity (log, masked), from that product's history features and an embedding.
- **Serving (`serve.py`):** next date and basket are read as of the last order ("we expected them on X, with this"); churn is read as of today. `days_overdue` is today minus the expected date.

## Data

`gen_data.py` writes `data/histories.json` (deterministic, two years: 2024-10-01 to 2026-10-17, 905 customers, 71,026 orders):

| Source | Customers | What it adds |
| --- | --- | --- |
| `profiles/batch_1..5.json` | 500 | Written by five parallel Claude Haiku agents, 100 each, one theme per batch: Milan bars, Lombardy restaurants, delis, neighbourhood grocers, seasonal lake/seaside/ski places and edge cases. Each profile has core products from the real catalogue, cadence, weekdays, yearly closures, summer and December demand, one-off events, yearly trend, churn, a product adopted and a product dropped. Validated by `check_profiles.py`. The numbers (orders, quantities) are generated by code from the profile, not by the LLM. |
| random generator | 400 | Kind-based baskets, cadence 5-28 days, summer bump, 12% churners, product adoption. |
| `../data/history` | 5 | The demo customers. Never used for training or testing. |

Split by customer, 70/15/15 (`model.split_ids`, ids starting `syn-` or `pf-`).

## Results (AMD Radeon Pro W7900D, 135 held-out customers)

Baseline: P-TopFreq (products in at least half of past orders, median quantity) and median cadence for the date, the strongest simple method in Li et al., "A Next Basket Recommendation Reality Check", ACM TOIS 2023. Full output: `logs/backtest_amd.log`, `backtest.json`.

| Last order of each test customer | Model | Baseline |
| --- | --- | --- |
| Basket F1 | **0.823** | 0.803 |
| Basket recall | **0.898** | 0.850 |
| Basket precision | 0.786 | 0.790 |
| Quantity exact | 0.596 | 0.590 |
| Next-date error | 2.81 days | 2.82 days |
| Date within ±2 days | **67.4%** | 65.9% |
| Churn AUC (12,401 snapshots) | 0.939 | **0.962** |

On 790 summer orders the quantity error drops from 0.83 to 0.66 (model vs baseline). Reading: the model beats the baseline on the basket by 2-5 points, ties it on the date and loses on churn. The churn probability ranks customers well but is not calibrated: a customer silent for 44 days on a 10-day cadence gets 2.7% while regular customers get about 0%.

### Learning curve

`learning_curve.py` retrains from scratch on growing subsets and tests on the same 135 customers (40 epochs each, AMD W7900D, `logs/lc_amd.log`, `learning_curve.json`):

| Train customers | Basket F1 | Quantity exact | Date error |
| --- | --- | --- | --- |
| 25 | 0.705 | 49.6% | 3.21 d |
| 50 | 0.787 | 52.6% | 3.41 d |
| 100 | 0.802 | 52.6% | 3.18 d |
| 200 | 0.812 | 56.7% | 3.08 d |
| 630 | 0.810 | 60.3% | 2.96 d |
| baseline | 0.803 | 59.0% | 2.82 d |

The basket passes the baseline at about 100-200 customers; quantities keep improving with data; the date does not reach the baseline.

## Run

On the AMD notebook (GitHub is not reachable from it: upload a tarball of `model/*.py`, `model/profiles`, `data/catalog.json`, `data/customers`, `data/history`):

```bash
python3 gen_data.py
python3 train.py --epochs 40     # prints "device: cuda (AMD Radeon Pro W7900D) torch ...+rocm..."
python3 backtest.py
python3 learning_curve.py        # optional, ~10 min on the W7900D
PORT=8077 PREDICT_TOKEN=secret python3 serve.py
```

The same commands run on an AMD Instinct MI300X in a `rocm/pytorch` container, or on CPU (`MODEL_DEVICE=cpu`). CatOrder reaches the service through `PREDICT_BASE_URL` and `PREDICT_TOKEN`; answers are cached, so the demo survives a stopped service.

## API

`GET /health` → `{ok, device, model}`.

`POST /predict` (`Authorization: Bearer $PREDICT_TOKEN` when set; 401 otherwise, 400 on bad input):

```json
{"today":"2026-10-18","customer":{"id":"bar-ponterosso","kind":"bar"},
 "history":[{"date":"2026-10-08","lines":[{"sku":"ACQ-NAT-1L","qty":6}]}]}
```

Response: `next_order_date`, `expected_gap_days`, `days_since_last`, `days_overdue`, `p_churn`, `basket` (`[{sku, qty, p}]`, p >= 0.5, sorted by p), `model`, `device`, `latency_ms`. Unknown SKUs are ignored.

Test: `python3 test_serve.py`.
