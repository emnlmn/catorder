# CatOrder next-basket model (catorder-nbr-v1)

A small PyTorch model (122k params, 0.5 MB) trained on order histories. Per customer it predicts the next-order gap, churn probability and the next basket (SKUs and quantities). It is not an LLM and has no hand rules.

Architecture: the last 16 orders (per-SKU log1p qty, log gap, day-of-year and weekday sin/cos) go through a GRU. The GRU state, a customer-kind embedding and cadence context feed a trunk with four heads: Laplace log-gap (median), churn (no order within 60 days), and a shared per-SKU MLP giving inclusion logit (BCE) and log-qty (masked regression) from SKU history features and a SKU embedding.

Training data is synthetic (`gen_data.py`, 400 customers, seed fixed, 12% churners, summer seasonality, product adoption) plus the 4 real demo histories (never used for training or testing). Splits are by customer (70/15/15).

## Run on an AMD Instinct MI300X (AMD Developer Cloud)

```bash
# inside a rocm/pytorch container (torch with ROCm already installed; the GPU shows up as torch.cuda)
git clone <repo> && cd kept/model
pip install -r requirements.txt   # skip torch reinstall if the image already has it: pip install numpy
python gen_data.py
python train.py --epochs 40       # prints "device: cuda (AMD Instinct MI300X ...)"
python backtest.py
PORT=8077 PREDICT_TOKEN=secret python serve.py
```

`MODEL_DEVICE=cpu` forces CPU. Weights land in `weights/catorder-nbr.pt` and `weights/catorder-nbr.json` (vocab, hyperparams, metrics).

## API

`GET /health` returns `{ok, device, model}`.

`POST /predict` (header `Authorization: Bearer $PREDICT_TOKEN` if the env var is set; 401 otherwise, 400 on bad JSON or dates):

```json
{"today":"2026-10-18","customer":{"id":"bar-ponterosso","kind":"bar"},
 "history":[{"date":"2026-10-08","lines":[{"sku":"ACQ-NAT-1L","qty":6}]}]}
```

Response: `next_order_date`, `expected_gap_days`, `days_since_last`, `days_overdue` (0 if not overdue), `p_churn`, `basket` (`[{sku, qty, p}]`, p >= 0.5, sorted by p, qty rounded per sell_unit), `model`, `device`, `latency_ms`. Unknown SKUs are ignored.

Test: `python test_serve.py`.

Honest reading: the model ties the baselines on basket and date (differences are within noise on 60 customers) and the frequency baseline is slightly ahead on basket recall and on churn AUC. The synthetic data is generated by a near-stationary process, which the baselines already capture, so there is little headroom; the model's value is that it is a single learned model with calibrated probabilities that can be retrained on real order data, where seasonality, drift and cross-SKU patterns should give it room to beat the baselines.

## Learning curve (synthetic data)
`python3 learning_curve.py` (40 epochs, fixed 60-customer test set, last_order metrics; writes learning_curve.json, not the weights). Basket F1 climbs 0.66 / 0.80 / 0.86 / 0.88 / 0.89 for 25 / 50 / 100 / 200 / 280 train customers and meets the frequency baseline (0.885) at about 200; qty-exact (0.49 to 0.62, baseline 0.64) trails it, and date MAE and within-2d are flat or noisy (about 3.1 days, 0.62-0.67).
